# v1 — 分块 tile + shared memory

- **日期**：2026-10-21
- **文件**：`gemm_v1.cu`
- **前一版本**：v0（`ae13474`）

## Step 1 — 瓶颈（来自 v0 结论）

naive 是 **DRAM-bandwidth-bound**（4096³ 恰好压在 memory 斜线上），AI≈4.9，根因是数据被重复读 434 倍。

## Step 2 — 方案

把 C 切成 32×32 的块，每个 block 协作把 A/B 的 tile 搬进 shared memory，内层从 smem 复用数据累加到寄存器（每线程 2×2 个累加器）。

## Step 4 — 性能与精度验证

| 尺寸 | v0 TFLOPS | v1 TFLOPS | 提升 |
|---|---|---|---|
| 512³ | 1.62 | 2.71 | 1.7× |
| 2048³ | 1.69 | 3.20 | 1.9× |
| 4096³ | 1.26 | **3.24** | **2.6×** |

- 4096³ 相对峰值 2.73%，相对 cuBLAS（87.10）约 3.7%
- 精度：`max_rel_err = 8.1e-05`（2048³）、`9.5e-06`（512³），均 [PASS]（与 v0 一致，优化未引入额外误差）

## Roofline 重新定位

```
v1 AI = 3.24e12 / 255.6e9 ≈ 12.7 FLOP/byte   （v0 是 4.9）
```

**关键验证**：v1 仍精确压在 memory 斜线上（3.24 TFLOPS ≈ 255.6 GB/s × 12.7）。性能提升 2.6× 与 AI 提升 2.6× **完全同步**——印证了 roofline 的核心定律：**memory-bound 时，性能 ∝ 算术强度**。

## 结论

- tile 有效：AI 从 4.9 → 12.7，性能 1.26 → 3.24 TFLOPS，符合理论预期。
- 但仍 **memory-bound**：TM=TN=32 太小，理论 AI = T/2 = 16（实测 12.7），A/B 每个 tile 仍被 N/TN = 128 个 block 重复读，远没到"各读一次"的理想 AI=2048。
- 当前瓶颈不变：**算术强度仍太低（12.7 ≪ 463 转折点）**。

## 下一步（roofline 驱动）

继续提高 AI。方向是**加大输出 tile（TM/TN 32 → 128）**，AI 从 16 → 64。但这会撞上两个新约束，需要一并解决：

1. **寄存器压力**：TM×TN 的累加器总量 = 每线程累加器 × 线程数，tile 加大后每线程累加器暴增，需调整 block 大小或累加器布局；
2. **smem 访问效率**：tile 加大后 smem 读的模式（bank conflict、向量化）开始影响性能，不再是"搬进去就完事"。

预期：若能把 AI 提到 64，性能上限 ≈ 255.6 × 64 ≈ 16 TFLOPS（仍是 memory-bound，但比当前 3.24 高约 5 倍）。
