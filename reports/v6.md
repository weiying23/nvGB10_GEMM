# v6 — 两次尝试 + 教训沉淀（未采纳）

- **日期**：2026-10-26
- **文件**：`gemm_v6.cu`（两个变体，均未达到 v3 水平，未采纳）
- **前一版本**：v5（`3223125`）

## v6 两次尝试

### 尝试 1：B 的 ldsm 从 x2 换 x4（减少 ldsm 条数 3→2）

**假设**（来自消融探针）：ldsm 条数太多（3 ldsm : 2 mma）压垮发射。
**实测**：精度 PASS 但性能 **-2%**（25.6 vs 26.1 @2048³）。
**证伪**：判别探针证实 **B 依赖代价与指令变体无关**（x4.trans 的 B 依赖 = 53.7 TFLOPS，与 x2 的 55.2 相同）——代价在 mma 的 **B 操作数依赖路径本身**（v5 定位的主因），换指令不能消除。

### 尝试 2：WN=32（每 warp 4 mma）+ B x4

**假设**（来自 ilp 探针）：4 个独立 mma 能摊薄 ldsm 延迟（探针实测 115 TFLOPS = 98% 峰值；注：该探针 B 用固定值，覆盖的是 A 侧 -9% 的次要因素）。
**实测**：精度 PASS 但性能 **-20%**（20.9 vs 25.9 @2048³）。寄存器 36→48、occupancy 掉 29%。
**证伪**：ilp 探针是「纯计算」（B 用固定值、无 cp.async），真实 gemm 里加大 WN 会让 **B 的 ldsm+cp.async 全部翻倍** + occupancy 下降，两头抵消摊薄收益。完整 kernel 的 B 依赖（主因，-51%）需要 v7 的 8× 片段复用才摊薄。

## 沉淀的教训

1. **探针结论不能直接外推到完整实现**：探针隔离了单一变量（如 4 mma 摊薄延迟），但完整 kernel 有耦合副作用（B 访存翻倍、occupancy 下降）。探针定位「方向」，完整实测定「采纳」。
2. **加大 tile 有两种方式，效果完全相反**：
   - ❌ 更多 warp（block 512/1024，v4/v6 尝试2）：syncthreads 变贵 + occupancy 下降，双输；
   - ✅ 更大 warp tile（cuBLAS 方式）：block 仍是 256 线程，每 warp 从 16×16 吃到 64×64。
3. **消融探针是定位指令级瓶颈的唯一手段**（本机 ncu 权限锁）：逐项排除法（带宽 130TB/s 排除、条数排除、bank conflict 排除、syncthreads 排除、指令变体排除、发射位置排除）最终定位到「**mma 的 B 操作数依赖路径**（ldsm → mma，-51%），A 侧仅 -9%」——软件 roofline 完全看不到这一层。
4. **nsys 抓 cuBLAS kernel 名 = 看到标准答案**：cuBLAS 4096³ 用的就是 `cutlass_80_tensorop_bf16_s16816gemm_128x256_32x3`——**与我们完全相同的 mma.sync m16n8k16 指令**，配置（tile 128×256×32、8 warps、每 warp 64×64、3 stage）全部公开在 CUTLASS。

## 关键结论（v7 的依据）

cuBLAS 87 TFLOPS vs 我们 26 的差距，不在指令，在策略：

| | cuBLAS | 我们 v3 |
|---|---|---|
| warp tile | **64×64（32 mma、128 累加器）** | 16×16（2 mma、8 累加器） |
| occupancy | 极低（~230 寄存器/线程，1-2 block/SM） | 高（36 寄存器，7 block/SM） |
| 策略 | **低 occupancy 换极高 ILP** | 高 occupancy 低 ILP |

**v7 方向：照抄 CUTLASS 128×256×32 配置**——8 warps 不变，每 warp 64×64，3 stage，接受低 occupancy。
