# v0 — baseline：朴素 GEMM（global 直算，无优化）

- **日期**：2026-10-21
- **文件**：`gemm_v0.cu`
- **阶段**：消融表起点（性能天坑底线）

## 实现

每个线程计算 `C[row][col]` 的一个元素，K 循环内直接读 global：

```cuda
for (int k = 0; k < K; ++k)
    acc += __bfloat162float(A[row*K+k]) * __bfloat162float(B[k*N+col]);
```

无分块、无 shared memory、无寄存器复用、无张量核。

## 性能（峰值 118.37 TFLOPS）

| 尺寸 | A+B 数据量 | TFLOPS | 占峰值 | 相对 cuBLAS |
|---|---|---|---|---|
| 512³ | 1 MB | 1.62 | 1.37% | ~1.9% |
| 1024³ | 4 MB | 1.68 | 1.42% | ~1.9% |
| 2048³ | 16 MB | 1.69 | 1.43% | ~1.9% |
| 4096³ | 64 MB | **1.26** | 1.07% | ~1.4% |

## 精度（vs cuBLAS 同精度 BF16，参照 §5.2）

```
正确性 vs cuBLAS: max_abs_err=3.2e-05  max_rel_err=9.5e-06  rel_L2=4.2e-07  [PASS]
量化损失 vs FP32: max_rel_err=6.5%（512³, K=512，非正确性判据）
```

## Step 1 — Roofline 瓶颈分析

本机 roofline（实测）：

- compute 上限 = 118.37 TFLOPS，memory 上限 = 255.6 GB/s
- **转折点 = 118.37e12 / 255.6e9 ≈ 463 FLOP/byte**

naive 在 4096³ 的位置：

```
AI = 1.26e12 / 255.6e9 ≈ 4.9 FLOP/byte
```

- **判定：DRAM-bandwidth-bound**（1.26 TFLOPS 恰好压在 memory 斜线上，DRAM 被打满）
- 512~2048³ 为 L2-bound（数据 <24MB 全进 L2），本质同为访存受限

**根因**：算术强度太低。naive 的 DRAM 读量 = 137.4 GFLOP / 4.9 ≈ 27.8 GB，而 A+B 总量仅 64 MB —— **同样的数据被重复读了 434 倍**（每线程独立从 global 取数，零复用）。

## 结论与下一步

- 当前瓶颈：**算术强度过低（4.9 ≪ 463），memory-bound**
- 优化方向（roofline 驱动）：**提高数据复用**，把 AI 从 4.9 拉向理想值 2048（A、B 各只读一次），跨过 463 转折点进入 compute-bound
- 下一步措施：**分块 tile + shared memory**（`gemm_v1.cu`），block 内协作把 A/B tile 搬进 smem 复用
- 预期：4096³ 从 1.26 TFLOPS 显著提升（首版 tile 通常到 20~40 TFLOPS，尚未做 TMA/流水线）
