# v9 — padded smem 布局消除 LDSM bank conflict：+25% ✅ 采纳

- **日期**：2026-11-01
- **文件**：`gemm_v9.cu`
- **前一版本**：v8（59.2 @4096³）

## Step 1 — Roofline 与发现链

### 前情（v8 之后的三步探针）

1. 片段寄存器双缓冲（CUTLASS `mac_loop_iter` 结构）实测零提升（58.7 vs 59.2）→ ldsm→mma 程序序非瓶颈；
2. 反向确认 v8 = 77（零同步探针墙）- 18（同步协议 -9 + 杂项 -8）；
3. **cuBLAS 87 > 77 之谜**：同指令构成（16 ldsm + 64 mma/迭代）却比我们零同步的墙还高 10 → 它必然改变了 ldsm 的成本本身。

### Bank conflict 完整机理（本节为教学详解）

**smem 的物理结构**：shared memory 分 32 个 bank，每 bank 宽 4B，**按字节地址轮转分布**——字节 0–3 在 bank 0、4–7 在 bank 1、……、124–127 在 bank 31，然后 128–131 又回到 bank 0。即 **128B 为一个完整周期（8 个 16B 槽）**。一条 warp 指令的多个 lane 若落在**同一个 bank**，访问被串行化——这就是 bank conflict（同一周期只能服务每 bank 一个 4B 请求）。

**LDSM 的特殊性**：`ldmatrix` 是 warp 级 gather——每个 lane 提供一个 **16B 行段地址**（不是各读各的标量）。`x4` = 32 个地址 = 4 张 8×8 矩阵 × 8 行。**无冲突的充要条件：每张 8×8 矩阵的 8 个 16B 段落在 8 个互异的 16B 槽（mod 128B）**——正好铺满一个 128B 周期，32 bank 各服务一次。

**行距决定一切**：设 smem 行距为 S（16B 的倍数），第 r 行的槽号 = (r·S/16) mod 8。8 行互异 ⟺ **S/16 为奇数**。由此得到反直觉的槽位表：

| 行距 S | S/16 | 8 行槽号 | 冲突 |
|---|---|---|---|
| 16B（8×8 连续存放） | 1 | {0,1,2,3,4,5,6,7} | 无（理想） |
| **64B（旧 `As[128][32]`）** | 4 | {0,4,0,4,0,4,0,4} | **4 路** |
| **128B** | 8 | {0,0,0,0,0,0,0,0} | **8 路（最坏！）** |
| **512B（旧 `Bs[32][256]`）** | 32 ≡ 0 (mod 8) | {0,0,0,0,0,0,0,0} | **8 路** |
| **80B（v9 的 A padding）** | 5 | {0,5,2,7,4,1,6,3} | 无 |
| **528B（v9 的 B padding）** | 33 ≡ 1 (mod 8) | {0,1,2,3,4,5,6,7} | 无 |

注意两个反直觉点：① **行距对齐到 128B 是最坏情况**（8 行全撞槽 0）——"对齐越好"在这里恰恰相反；② 512B 行距的 B 布局就是 128B 整数倍，天然 8 路全撞。

**为什么叫"swizzle 没做过"**：本项目 v7 做的是 **block swizzle**（grid 级：block↔tile 的分配顺序，解决 L2 复用），与 **smem bank swizzle**（数据在 bank 里的落位，解决 LDSM 冲突）同名不同层。v7 的 swizzle 不改变任何字节在 smem 里的位置，所以冲突一直存在——只是所有"swizzle 已做"的心理检查项都被 block swizzle 错误地勾掉了。

**消除冲突的三种手段**（同族不同法，v9 用第 1 种）：

| 手段 | 机制 | 代价 |
|---|---|---|
| **Padding**（v9） | 行距 +8 列（64→80B、512→528B），S/16 变奇数 | smem 浪费 ≈11%（24→27KB/stage）；TMA 写不了（box 内必须连续） |
| **XOR swizzle**（CUTLASS sm80 经典） | 落位时 `槽号 ^= (行号 & 7)`，加载/读取两侧做同样映射 | 零浪费，但两侧地址都要做 XOR |
| **TMA `SWIZZLE_128B`**（nvjet/Hopper+ 路线） | **TMA 引擎写入时硬件自动做 XOR**，kernel 只需读取侧映射 | 需 box 内维 ≤128B（B 要拆 4 个 box、配套 BK=64） |

**本项目实测案例**（微基准 `bench/probe_ldsm.cu`，同一条 `ldmatrix.x4` 指令纯吞吐）：

| 布局 | 时间 | 相对无冲突 |
|---|---|---|
| A 模式（64B 行距） | 5.30 ms | **4.0×**（4 路 ✓ 预测命中） |
| A-padded（80B 行距，对照） | 1.33 ms | 1× |
| B 模式（512B 行距，.trans） | 10.60 ms | **8.0×**（8 路 ✓ 预测命中） |

**kernel 级验证**（`bench/probe_v7cyc.cu` vs `probe_v7pad.cu`，零同步计算探针换 padded 布局）：

| 布局 | TFLOPS |
|---|---|
| 旧布局（4 路 + 8 路冲突） | 76.78 |
| **padded（零冲突）** | **112.42（+46%）** |

**"77 墙"完全是 bank conflict 伪影**：零冲突后 ldsm 成本只剩 -3.8（112.4 vs 纯 mma 116.2）。此前所有"距 cuBLAS 差距"分析（sync-bound、ldsm 依赖、流水深度）都被这个伪影污染——因为 v5 时代的"纯 ldsm 带宽 130 TB/s、带宽排除"探针用的是无冲突寻址模式，**探针的寻址模式必须与真实 kernel 逐位一致**，否则测的是另一个问题。

## Step 2 — 方案

**Padding**：A 行距 64B→80B、B 行距 512B→528B。

- 80B = 5×16B，5 与 8 互质 → r×5 mod 8 = {0,5,2,7,4,1,6,3} 全互异；
- 528B = 33×16B，33 mod 8 = 1 → r×33 mod 8 = r，全互异。

约束：**TMA 写不了 padded 布局**（box 内必须连续）→ 本版回到 cp.async 加载。v8 已实测 TMA 的加载收益 ≈ 0（+1%），真正的 TMA 路线是 `SWIZZLE_128B` 模式（nvjet 架构，BK=64），属后续版本。

## Step 3 — 实现

相对 v7 **只改 smem 数组声明**（`BK+8` / `BN+8`），加载与 ldsm 寻址经二维数组类型自动适配；smem 72KB→79.5KB（3-stage 仍 ≤99KB），寄存器 200，1 block/SM 不变。

## 结论：采纳 ✅

**v0→v9 最大的单点发现**：瓶颈不在指令、不在同步、不在流水结构，而在**寻址布局的 bank 冲突**——三周来所有"距离 cuBLAS 的差距"分析（sync-bound、ldsm 依赖、流水深度）都被这个伪影污染。

### 本轮的方法论收获

1. **LDSM 布局有隐性冲突税**：`[M][K]/[K][N]` 直存布局在这类 tile 形状下必冲突（64B/512B 行距），无冲突要求行距 ≡ 16B×(与 8 互质) —— smem 布局必须按 bank 结构设计，不是"能放下就行"；
2. **探针的对照必须包含布局本身**：v5 时代"纯 ldsm 带宽 130 TB/s、带宽排除"的结论用的是无冲突模式，未暴露真实 kernel 的冲突——探针的寻址模式必须与被测 kernel 逐位一致；
3. **负结果的版本不留版号**（双缓冲实验降级为 v8 附加探针，本轮 v9 版号给了确认收益的 padding）。

## 关键代码（对照 `gemm_v9.cu` 阅读）

本版核心改动**只有 smem 数组声明一处**（v7 → v9 的全部 diff，加载与 ldsm 寻址零改动）：

```cuda
// v7（bank conflict 版）：
bf16 (*As)[BM][BK]   = reinterpret_cast<bf16 (*)[BM][BK]>(smem_raw);     // 行距 64B  → LDSM 4 路冲突
bf16 (*Bs)[BK][BN]   = reinterpret_cast<bf16 (*)[BK][BN]>(smem_raw + ...); // 行距 512B → LDSM 8 路冲突

// v9（padded 版）：行距 +8 列，S/16 变奇数 → 8 行落 8 个互异 16B 槽（mod 128B）
bf16 (*As)[BM][BK + 8] = reinterpret_cast<bf16 (*)[BM][BK + 8]>(smem_raw);          // 行距 80B = 5×16B，5 与 8 互质
bf16 (*Bs)[BK][BN + 8] = reinterpret_cast<bf16 (*)[BK][BN + 8]>(                      // 行距 528B = 33×16B，33 mod 8 = 1
    smem_raw + NUM_STAGES * sizeof(bf16) * BM * (BK + 8));
// smem 总量：3 × (128×40 + 32×264) × 2B = 79.5KB（≤99KB，3-stage 仍放得下）
```

**为什么其余代码零改动**——C 二维数组类型自带行距，`&As[s][row][col]` / `&Bs[s][k][n]` 的地址计算（加载侧 cp.async 目的地址、读取侧 ldmatrix 源地址）全部自动适配新行距。这正是 padding 相对 XOR swizzle 的工程优势：**后者要求加载和读取两侧手写同样的 XOR 映射，前者只改类型声明**。

代价对照（三种修复手段的实现成本）：

| 手段 | kernel 侧改动量 | smem 浪费 |
|---|---|---|
| padding（本版） | 1 处声明 | ~11%（24→27KB/stage） |
| XOR swizzle | 加载地址 + ldsm 地址两侧都加 XOR 映射 | 0 |
| TMA SWIZZLE_128B | tensor map 建 4 个 B box + ldsm 侧 XOR 映射（BK=64 重构） | 0 |

**探针复现**（两份证据的源码都在 bench/）：
- `probe_ldsm.cu`：同一条 `ldmatrix.x4` 在 64B/80B/512B 行距下的纯吞吐（4.0×/1×/8.0×）；
- `probe_v7cyc.cu` vs `probe_v7pad.cu`：零同步计算探针换 padded 布局（76.8 → 112.4），证明"77 墙"是冲突伪影。

**学习要点**：① bank conflict 的判定不需要跑代码——行距/16 是否为奇数，纸面一步算出（本版从分析到验证到修复只用了一轮探针）；② 最危险的布局是行距恰为 128B 整数倍（"对齐好"反而 8 路全撞）；③ 真实 kernel 与探针的**寻址模式必须逐位一致**，否则探针测的是另一个问题（v5 的"带宽排除"教训）。

## 下一步计划（按优先级）

### 1. v10 主攻：TMA + `SWIZZLE_128B` + BK=64（nvjet 正统路线）

**为什么是它**：v9 的 padded 与 v8 的零同步目前互斥——v8 的 mbarrier full 依赖 TMA 的 `complete_tx`，而 **TMA 写不了 padded 布局**（box 内必须连续）。`SWIZZLE_128B` 模式让 TMA 写入时硬件自动做 XOR 交错，**同时拿到"零 bank conflict + TMA + 零 `__syncthreads`"三件收益**，这也是 nvjet 全系配置（BK=64、2-stage）的做法。

| 项 | 方案 |
|---|---|
| tile | 128×256×**64**（A box {64,128}=128B 内维 ✓；B 拆 4 个 {64,64} box） |
| smem | 48KB/stage × **2-stage** = 96KB（≤99KB；lookahead 字节 2×96KB 与 v9 的 3×27KB 相当） |
| mma 循环 | 每 K 块 4 个 k16 slice（v9 是 2 个） |
| ldsm | 读取侧做与 swizzle 相同的 XOR 槽位映射 |
| 预期 | 67.9 + 零同步(~8%) + 布局收益 → **78~85**（cuBLAS 87.1 为参照） |
| 风险 | B 拆 4 box 后 TMA 发射×5/stage（thread 0 仍无压力）；swizzle 地址映射错一个槽位就是精度错误（用 dump 法验证） |

### 2. 中小形状配置族（autotune 分发表）

针对 512³~2048³ 的 SM 填充病（1024³ 只有 32/48 block、512³ 闲置 83% SM）：
- 小 tile 变体（如 128×128 → 1024³ 得 64 block）或 split-K（K 分段 + 归约）；
- v4 的参数化模板是现成底子，tile/ldsm/写回代码不变，只换常量与 grid 映射；
- 目标：1024³ 从 59% 拉到 ~75%（填充 67%→100% 是上限 1.5×）。

### 3. epilogue 重叠（对 2048³ 的 17% 写回扎堆）

写回当前 tile 时预取下一 tile（需要 tile 间流水，接近 persistent 的收益面但不必做 persistent——引擎地图实测 cuBLAS 也没用 persistent）。

**顺序依据**：① 是天花板（78%→85+）且机制全部前置验证过（TMA ✓ mbarrier ✓ swizzle 机理 ✓）；② 独立于 ①，随时可做；③ 依赖 tile 间流水的结构改动，放最后。
